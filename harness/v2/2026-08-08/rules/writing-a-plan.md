# plan 을 쓰는 규칙

[`work-an-issue`](../workflows/work-an-issue.md)의 10단계가 요구하는 도메인 경계 ·
스키마 · 권한에 더해, 아래 둘을 `plan.md`에 적는다.

## 실패 경로를 적는다

정상 경로만 적은 계획은 반쪽이다. 아래가 이 변경에 해당하면 **어디서 처리하고 무엇을
돌려주는지**를 적는다.

| 상황 | 적을 것 |
|---|---|
| 같은 대상에 요청이 겹친다 | 무엇으로 막나(락 · 유니크 제약), 나중 요청은 어떤 응답을 받나 |
| 기다리다 시간이 초과된다 | 상한이 몇 초인가, 넘으면 어떤 응답인가 |
| 외부 시스템이 실패한다 (메일 · Drive · GCS · FCM) | 트랜잭션이 되돌아가나, 사용자에게 무엇이 보이나 |
| 일부만 성공한다 | 남은 것을 누가 언제 정리하나 |

**락이나 재시도를 넣으면 상한을 적는다.** 대기 시간의 상한, 재시도 횟수의 상한.
**「상한을 두지 않는다」도 답이다** — 그렇게 정했으면 이유와 함께 그렇게 적는다.
적으라는 것이지 만들라는 것이 아니다. #225에서 이 줄을 «구현한다»로 읽고 제한 시간을
넣었다가, 예외 갈래와 DB별 차이가 번져 도로 걷어냈다.

## 질의를 적는다

목록 조회나 스키마가 바뀌면 표로 적는다.

| 누가 | 어떤 조건으로 | 몇 행을 읽나 | 얼마나 자주 |
|---|---|---|---|
| 관리자 수업 목록 | 날짜 범위 + 상태 | 페이지 크기(최대 100) | 화면을 열 때마다 |

- **예상 행 수를 적는다.** 매일 늘어나는 테이블(`lessons` · `daily_schedules` ·
  출석 · 요청)과 거의 안 늘어나는 테이블(`classrooms` · `departments`)은 같은
  코드가 다른 결과를 낸다.
- **인덱스를 더하면 그것을 쓰는 질의를 옆에 적는다.** 질의 없이 만든 인덱스는
  추측이고, 쓰기 비용만 늘린다.
- 목록은 DB에서 페이징한다. 전체를 읽어 메모리에서 자르는 계획은 행 수가 늘지
  않는다는 근거가 있을 때만 쓴다.

## 단계마다 판정 기준을 단다

「~를 구현한다」로 끝나는 작업은 끝났는지 알 수 없다. 작업마다 **무엇이 통과하면
끝인지**를 한 줄로 적는다 — 어떤 테스트, 어떤 명령.

## 어긋났을 때 알아채는 법

계획에 「동시에」 · 「실패하면」 · 「초과하면」이 한 번도 안 나오면 실패 경로가 빠진 것이다.
인덱스가 diff에 있는데 계획에 행 수가 없으면 추측으로 만든 것이다.
