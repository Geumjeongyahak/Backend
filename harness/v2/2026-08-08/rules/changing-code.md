# 있는 코드를 고치는 규칙

## 고치기 전에 호출자를 전부 찾는다

공유 메서드 · 응답 DTO · 스키마를 고칠 때는 그것을 부르는 자리를 다 본 뒤에 손댄다.

```bash
grep -rn "<메서드 이름>" src/main/java src/test/java
```

증상이 보고된 경로 하나만 고치면 나머지 호출자는 깨진 채 남는다.

## 모든 호출자가 지나는 한 곳을 고친다

같은 수정이 호출자마다 복사되고 있으면 고칠 자리를 잘못 고른 것이다. 가드 하나를
공유 지점에 두는 것이 호출자 다섯에 하나씩 두는 것보다 작고, 여섯째 호출자가 생겨도
안 빠진다.

## 고치라는 것만 고친다

지나가는 김에 한 이름 변경 · 포맷 변경이 diff에 섞이면 리뷰가 진짜 변경을 못 본다.
눈에 띈 다른 결함은 고치지 말고 PR의 `리뷰어에게`에 적거나 이슈로 남긴다.

## 필요한 것만 만든다

고치는 데 필요 없는 것을 같이 만들지 않는다. 하나를 더하면 그것이 실패하는 경우가 따라
오고, 그 경우를 다루는 코드와 테스트가 또 따라온다. 더하기 전에 순서대로 묻는다.

1. 이것 없이도 맡은 결함이 고쳐지나 — 그렇다면 만들지 않고 계획의 「안 하는 것」에 적는다
2. 이 레포에 이미 있나 — 있으면 그것을 쓴다
3. 프레임워크나 DB가 해 주나 — 해 주면 코드로 다시 만들지 않는다
4. 설정 한 줄로 되나 — 되면 클래스를 만들지 않는다

**실패 경로가 셋째 갈래로 번지면 멈춘다.** 처음 더한 것이 필요했는지부터 다시 본다.

## 말하기 전에 본다

「괜찮다」 · 「문제다」 · 「없다」는 본 다음에 말한다. 로그는 뽑아 보고, 제약은 스키마에서
찾고, 설정값은 그 값을 쓰는 곳을 다 찾은 뒤에 말한다. 다른 도구(리뷰 · 검색 에이전트)가
낸 결론도 원본에서 한 번 확인한 뒤 옮긴다.

[`mistakes-ledger.md`](../../../mistakes-ledger.md)에서 이 갈래가 네 번 나왔다 — 작성자
분류, 배포 경로, 유니크 제약, 스택트레이스 길이.

## 커밋에 담기 전에 본다

`git add -A`를 폴더째로 쓰지 않는다. 담을 경로를 이름으로 적고, 커밋 전에
`git status --short`로 무엇이 담겼는지 본다. 전역 설정 · 전역 예외 처리기 · 공용 클래스를
고칠 때는 이 변경이 닿는 다른 자리를 먼저 센다.

## 어긋났을 때 알아채는 법

같은 몇 줄이 두 파일 이상에 복사됐으면 공유 지점을 놓친 것이다.
리뷰에서 「이 경로만 쓰는 줄 알았다」가 나오면 호출자를 안 센 것이다.
커밋 뒤 `git status`가 비어 있는데 안 담으려던 파일이 있었다면 범위 밖 파일이 같이 들어간 것이다.
