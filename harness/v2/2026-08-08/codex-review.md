# codex 리뷰 — 다른 눈

v2에는 적대적 리뷰를 맡는 직군이 없다. `codex review` CLI가 그 자리다. **다른
프로세스이고 다른 모델이라 그것만으로 다른 눈이 된다.** 자기가 짠 것을 자기가
판정하지 않는 것이 이 도구를 두는 이유의 전부다.

## 언제 부르나

**병합 게이트가 아니다. PR마다 돌리지 않는다.** 한 줄짜리 변경에 회차와 기록이 통째로
붙으면 아무도 안 지키게 되고, 안 지키는 규칙은 없는 규칙이다.

부르는 자리는 하나다. **변경이 여러 파일에 걸치거나 구조가 바뀌었을 때, 마지막에 한 번.**

| 부른다 | 안 부른다 |
|---|---|
| 여러 파일에 걸친다 | 한 파일 몇 줄 |
| 도메인 경계·이벤트 계약이 바뀐다 | 값 하나, 설정 한 줄 |
| 엔티티·스키마가 바뀐다 | 오타·문구 |
| 새 엔드포인트가 생긴다 | 문서만 고침 |

안 부르고 병합해도 된다. 다만 **한 번 부르기로 했으면 수렴할 때까지 돈다.** 남은
`P1`·`P2`를 두고 병합하지 않는다.

## CLI만 쓴다

GitHub의 `@codex review` 클라우드 봇은 왕복이 5~15분이라 고칠 때마다 느리고 회차를
우리가 못 정한다. 리뷰는 전부 로컬 CLI로 돈다.

```bash
codex review "$(cat harness/v2/2026-08-08/codex-review-prompt.md)"
```

**리뷰 지침을 반드시 같이 넘긴다.** 그냥 돌리면 이 레포를 몰라서 오탐이 난다 —
이벤트 기반 통신을 «불필요한 간접 호출»로 지적하는 식이다.

`--base`·`--uncommitted`·`--commit`은 프롬프트와 같이 못 쓴다
(`error: --base cannot be used with [PROMPT]`). 그래서 범위 플래그 대신 **어디까지
볼지를 프롬프트 첫 줄에 문장으로 적는다.**

새로 만든 파일은 커밋한 뒤 리뷰하거나 `git add -N <파일>`로 diff에 올린다. 안 그러면
새 파일이 통째로 안 보인다.

## 회차가 제대로 끝났는지

전경에서 시간 상한을 걸고 돌린다. 백그라운드로 띄우면 죽어도 모른다.

| 신호 | 뜻 | 조치 |
|---|---|---|
| 출력이 비었음 | **회차가 실패한 것이다. 통과가 아니다** | 한 번 재시도, 또 비면 사람에게 보고 |
| 10분 초과 | 정상 회차는 2~4분 | 죽이고 범위를 좁혀 재시도 |
| 지적도 `P1·P2 없음`도 없음 | 형식을 못 지킨 것 | 재시도한다. 통과로 세지 않는다 |

**못 찾은 것과 없는 것은 다르다.** 출력이 깨졌을 때 0건으로 세면 그것이 곧 실패
은폐다. 「없다」고 적힌 것을 확인하고 넘어간다.

## 지적을 받는 법

**검증하고 받아들이지, 사회적으로 동의하지 않는다.** 지적이 맞는지 코드를 읽어
확인한 다음에 고친다. 확인 없이 고치는 것과 확인 없이 반려하는 것은 같은 실수다.

**리뷰어가 붙인 등급은 주장이지 사실이 아니다.** `blocking`이라고 적혀 있어도 그것을
근거로 삼지 않는다. 판단은 받는 쪽이 한다.

고치는 것은 하나다. **이번 diff가 깨뜨린 것을, 재현 경로와 함께 짚었을 때.**

| 반려 | 왜 |
|---|---|
| 재현 경로가 없다 | 어떤 입력·상태에서 무엇이 되는지를 못 대면 추측이다 |
| 지금 동작을 안 읽었다 | 이미 그렇게 도는 것을 고치라고 한다 |
| 원래 있던 것이다 | 이번 변경이 만든 게 아니다. 원장에 적고 다음으로 |
| 없던 것을 만들라 한다 | CI·의존성·모듈. 무엇을 더 만들지는 사람이 정한다 |
| 문체·표 정리 | 병합을 막지 않는다 |

**반려를 세지 않는다.** 열 건 중 아홉을 반려해도 그게 맞으면 맞는 것이다. 다
받아들이면 없는 함정을 피하는 구조가 남고, 그건 코드보다 되돌리기 비싸다.

반려는 사유를 한 줄로 남기고 다음 회차 프롬프트에 실어 같은 논쟁을 반복하지 않는다.

## 한 회차에 몰아서 고친다

지적 하나 고치고 리뷰, 또 하나 고치고 리뷰. 이렇게 하면 회차가 스무 개가 된다.

**그 회차에서 수용한 것을 전부 고친 뒤에 다음 리뷰를 돌린다.**

같은 종류는 지적된 줄만 고치지 말고 코드 전체를 훑어 고친다. "N+1"을 한 곳만 고치면
다음 회차에 옆 서비스에서 같은 것이 나온다.

## 회차 예산 3회

비싼 건 리뷰 한 번(2~4분)이 아니라 회차 수다.

| 회차 | 무엇을 고치나 |
|---|---|
| 1~2 | 수용한 것을 전부 한 번에 고친다 |
| 3 | 마지막. `blast`·`blocking`만 고치고 `local`·`speculative`는 원장에 적고 후속으로 |
| 4 이상 | 예외다. 왜 3회에 못 끝냈는지 적고 들어간다. 대개 설계가 틀렸다는 신호다 |

마지막에 전체 범위로 한 번 확인하는 것은 예산에 안 넣는다.

**같은 파일·같은 종류가 3회째 나오면 패치를 멈춘다.** 그 자리는 설계가 틀린 것이다.
조건을 하나 더 붙이지 말고 무엇을 근거로 판단할지를 바꾼다.

## 끝나는 조건

**전체 범위(`dev` 대비) 회차에서 `P1`·`P2`가 0건.**

증분 회차에서 0건이 나와도 그대로 병합하지 않는다. 증분만 보면 파일 사이의 상호작용을
놓친다.

## 어디에 남기나

회차마다 세 곳에 남긴다. 셋이 서로 다른 것을 맡는다.

| 어디 | 무엇 | 누가 읽나 |
|---|---|---|
| `docs/issues/<번호>-*/review.md` | 회차·범위·**남은 P1·P2 숫자**·수용과 반려 | `land` 게이트가 판정에 쓴다 |
| PR 코멘트 | 회차 전문 | 사람이 GitHub에서 읽는다 |
| [`findings-ledger.md`](../../findings-ledger.md) | 지적 한 건이 한 행 | 재발을 관측한다 |

`review.md`에는 **판정에 쓰는 숫자만** 남긴다. 회차 서사를 쌓으면 아무도 안 읽는다.
무엇을 왜 고쳤는지, 왜 반려했는지는 커밋 메시지에 남긴다.

### PR 코멘트 형식

```markdown
codex CLI 리뷰 회차 N — HEAD `<SHA>` — 범위: 전체(dev 대비) | 증분(<SHA>..HEAD)

- [P1][blast] 요약 — file:line
  무엇 / 어떻게 / 왜   ← 리뷰어 원문 그대로
- [P2][local] 요약 — file:line
```

요약만 올리면 왜 그렇게 판단했는지가 사라진다.
