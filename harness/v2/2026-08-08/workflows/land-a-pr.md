# land-a-pr — 내보낸다

```text
land-a-pr <이슈 번호>
```

**성질: 협업.** 병합은 사람이 답한다.

`work-an-issue`가 끝난 브랜치를 받아 PR을 열고 병합까지 간다. 따로 시작할 수도 있다 —
이미 손으로 만든 브랜치를 이 양식에 태우는 것이 정상 사용이다.

## 단계

### 10 — 검증

**증거 없이 완료를 주장하지 않는다.** 원칙 하나가 이 단계의 전부다.

```bash
scripts/harness/verify.sh
```

출력을 봤을 때만 통과라고 적는다. 「통과할 것이다」와 「통과했다」는 다른 문장이고,
PR 본문에 들어가는 것은 뒤쪽이다.

`work-an-issue`의 40에서 이미 돌렸고 그 뒤로 코드가 안 바뀌었으면 다시 안 돈다.
**애매하면 돈다.** 전체 테스트 한 판이 애매한 판단보다 싸다.

### 20 — PR 본문

이 레포에는 `.github/PULL_REQUEST_TEMPLATE.md`가 없다. 양식은 최근 PR들이 갖고 있고,
그것을 따른다. `gh pr view <최근 번호> --json body -q .body`로 확인한다.

```markdown
## 개요

<무엇을 왜 바꿨는지 두세 문장>

## 변경 유형

- [ ] 새 기능 (feat)
- [ ] 버그 수정 (fix)
- [ ] 리팩토링 (refactor)
- [ ] 문서 수정 (docs)
- [ ] 테스트 (test)
- [ ] 기타 (chore)

## 변경 내용

- <엔드포인트·동작 단위로. 중첩 목록으로 세부를 붙인다>

## 관련 이슈

Closes #<번호>

## 스크린샷 (선택)

## 체크리스트

- [ ] 코드 컨벤션을 준수했습니다
- [ ] 테스트 코드를 작성/수정했습니다
- [ ] 머지 전 `./gradlew test`가 통과합니다
- [ ] 문서를 업데이트했습니다 (필요한 경우)

## 리뷰어에게

- <판단이 필요했던 자리. 안 한 것과 그 이유>
```

**`리뷰어에게`가 이 양식에서 제일 값나가는 절이다.** 무엇을 했는지는 diff가 말한다.
diff가 못 말하는 것은 «왜 저 방식이 아니었나»이고, 그것만 여기 적는다. 최근 PR들이
그렇게 쓰여 있다 — "기존 목록 API는 DB 페이징으로 변경하지 않고 N+1만 제거했습니다"
같은 문장이 리뷰어의 시간을 가장 많이 아낀다.

**체크리스트를 안 한 것까지 체크하지 않는다.** 빈칸이 정보다.

Mermaid는 흐름이 복잡할 때만 넣는다. 기준은
[`ideate-issue`](ideate-issue.md#30--specmd)와 같다. **코드에 없는 컴포넌트를
그리지 않는다.**

### 30 — PR 생성

**PR 제목은 이슈 제목을 그대로 쓴다.** 최근 5건이 전부 글자까지 일치한다
(PR #218 = issue #217 = `[FEAT] 월별 수업일지 조회 API 및 목록 조회 성능 개선`).

```bash
title=$(gh issue view <번호> --json title -q .title)
gh pr create --base dev --title "$title" --body-file <본문>
```

**커밋 메시지 형식이 아니다.** Conventional Commits(`feat(lesson): …`)는 커밋에만
쓰고, PR 제목은 `[FEAT]`·`[FIX]` 대괄호 접두사에 한국어 제목이다.

기준 브랜치는 `dev`다. 최근 머지된 PR이 전부 `dev` 기준이고, `main` 기준은 `hotfix/`
하나뿐이었다. **PR에 라벨은 안 단다** — 최근 15건 모두 라벨이 없다. 분류는 이슈가 갖는다.

### 게이트 `land` — 내보내도 되나

사람이 판정한다. 물음에 다음을 실어 보낸다.

```
검사: verify.sh <통과 / 실패 n건>
codex 리뷰: <P1·P2 없음 / 안 부름 / 남은 n건>
바뀐 파일: <n>개
마이그레이션: <있음 V<n> / 없음>
```

**마이그레이션이 있으면 되돌리기가 비싸다.** 그 사실을 게이트에 실어 보내는 이유의
전부다. 스키마가 바뀐 PR과 안 바뀐 PR은 같은 무게로 승인될 수 없다.

`codex 리뷰: 안 부름`은 그 자체로 막힘이 아니다. 한 줄짜리 변경에 리뷰를 강제하면
아무도 안 지킨다. 다만 **여러 파일에 걸쳤는데 «안 부름»이면 사람이 그것을 보고 판단한다.**

| 답 | 다음 |
|---|---|
| `승인` | 40으로 |
| `막힘` | 여기서 끝난다. 사유를 원장에 적는다 |

[`gates-ledger.tsv`](../../../gates-ledger.tsv)에 한 행을 적는다.

### 40 — 병합과 정리

고정하는 것은 둘이다.

- **CI가 통과한 뒤에 병합한다.** `gh pr checks <번호>`
- **자동 병합·자동 배포를 워크플로가 하지 않는다.** 사람이 누른다

```bash
gh pr checks <번호>
gh pr merge <번호> --squash --delete-branch   # 사람이 확인한 뒤
```

## 안 하는 것

**`dev` → `main` 릴리스는 이 워크플로가 아니다.** 이슈 하나의 PR과 6주치를 묶어
내보내는 것은 판단의 종류가 다르다. 지금 `dev`에 50커밋이 쌓여 있고, 그것을 이
양식으로 열면 `변경 내용` 절이 아무도 안 읽는 길이가 된다.
