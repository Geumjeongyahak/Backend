# ideate-issue — 무엇을 왜 할지 정한다

```text
ideate <요청 한 문장>
```

**성질: 협업.** 사람이 처음부터 끝까지 붙는다. 대화가 산출물이라 혼자서는 못 돈다.

여기서 코드를 고치지 않는다. 브랜치도 안 만든다. 나오는 것은 GitHub issue 하나와
그 이슈의 `spec.md` 하나다.

## 단계

### 10 — 맥락 읽기

기존 이슈·PR·코드를 먼저 본다. 없는 것을 새로 만들자고 하는 것과, 있는 것을 고치자고
하는 것은 이슈 본문이 달라진다.

```bash
gh issue list --limit 20 --state all
gh pr list --limit 10 --state all
```

유사 도메인의 코드와 문서를 읽는다. 이 레포는 도메인별로 갈라져 있으므로
(`domain/{request,lesson,users,...}`) 어느 도메인에 붙는 일인지를 먼저 정한다.

**두 도메인에 걸치면 통로가 둘이다.** 조회는 상대 도메인의 `*ProxyService`를 주입하고,
상태 변화·부수 효과는 이벤트로 보낸다. 어느 쪽인지를 이 단계에서 정해두면 설계가
갈리지 않는다.

### 20 — 구체화 (brainstorming)

**여기가 흐름의 시작점이다.** 개발 절차 전체가 이 대화에 붙어 있다.

**한 번에 하나씩 묻는다.** 질문을 뭉쳐서 던지면 사람이 앞의 것만 답하고 뒤는
흘린다. 답을 듣고 다음 질문을 정한다.

묻는 순서는 대체로 이렇다.

1. **무엇이 지금 안 되나.** 기능이 아니라 겪은 일을 먼저 듣는다
2. **누가 겪나.** 관리자·교사·학생 중 누구인지에 따라 권한과 화면이 갈린다
3. **지금은 어떻게 하고 있나.** 우회로가 있으면 그것이 요구사항의 기준선이다
4. **안 해도 되는 것은 무엇인가.** 여기서 `Out of scope`가 나온다

**모르는 것을 지어내지 않는다.** 답이 안 나오면 그것을 «미정»으로 남기고 이슈의
`추가 정보`에 적는다. 정해진 것처럼 써 두면 다음 사람이 그것을 결정으로 읽는다.

설계가 서면 **사람에게 보여주고 승인을 받는다.** 승인 없이 40으로 넘어가지 않는다.

대화의 결론은 이슈 템플릿의 절을 채울 수 있어야 한다. **이 레포는 템플릿을 실제로
지킨다** — 최근 이슈 10건 중 9건이 절 이름까지 그대로다. 절을 빼거나 이름을 바꾸지
않는다.

| 종류 | 템플릿 | 제목 | 라벨 | 절 |
|---|---|---|---|---|
| 기능 | `feature-request.md` | `[FEAT] …` | `enhancement` | 기능 설명 · 배경 · 상세 요구사항 · 참고 자료 · 추가 정보 |
| 수정 | `bug_report.md` | `[FIX] …` | `bug` | 버그 설명 · 재현 방법 · 예상 동작 · 실제 동작 · 스크린샷 / 로그 · 환경 정보 · 추가 정보 |

`config.yml`에 `blank_issues_enabled: false`가 걸려 있다. **빈 이슈를 만들 수 없다.**
둘 중 하나를 고르는 것이 첫 갈림길이고, 그 선택이 브랜치 접두사(`feat/`·`fix/`)와
PR 제목까지 따라간다.

`상세 요구사항`은 체크박스 목록이다. **체크할 수 없는 문장은 요구사항이 아니다.**
"사용성을 개선한다"는 못 체크하고 "반려 시 신청자에게 사유를 포함한 알림을 보낸다"는
체크한다.

범위를 `Must / Should / Out of scope` 셋으로 가른다. `Out of scope`가 비어 있으면
대개 안 자른 것이다.

### 30 — spec.md

이슈 본문보다 자세한 것이 필요하면 `spec.md`에 적는다. API 계약, 데이터 모델 변경,
상태 전이가 여기 온다. 이슈 본문은 «무엇을 왜»이고 spec은 «무엇으로»다.

```
docs/issues/<번호>-<slug>/spec.md
```

번호는 이슈를 만든 뒤에야 나온다. 그래서 **폴더는 40 다음에 만든다.** 그 전까지
spec은 대화 안에 있다.

Mermaid는 흐름이 복잡할 때만 넣는다. API 동작이면 `sequenceDiagram`, 관계 변경이면
`erDiagram`, 상태·권한이면 `stateDiagram-v2`. **다이어그램에 `TODO`나 아직 없는
컴포넌트를 그리지 않는다.** 설계 중인 것과 정해진 것이 그림에서 안 갈리면 다음 사람이
그림을 사실로 읽는다.

### 게이트 `spec` — 이 이슈로 작업을 시작해도 되나

사람이 판정한다. 물음에 다음을 실어 보낸다.

- 요구사항 몇 개 중 체크 가능한 것이 몇 개인가
- `Out of scope`에 무엇이 들어갔나
- 건드리는 도메인이 몇 개인가

**"괜찮아 보이나요"는 판정이 못 된다.** 숫자를 놓고 묻는다.

| 답 | 다음 |
|---|---|
| `승인` | 40으로 |
| `다시` | 20으로 되돌아간다 |
| `막힘` | 여기서 끝난다. 사유를 원장에 적는다 |

[`gates-ledger.tsv`](../../../gates-ledger.tsv)에 한 행을 적는다.

### 40 — 이슈 생성

```bash
gh issue create --title "[FEAT] <제목>" --label enhancement --body-file <본문>
gh issue create --title "[FIX] <제목>"  --label bug         --body-file <본문>
```

`--body-file`로 만들면 템플릿을 우회하므로 **라벨이 자동으로 안 붙는다.** 위처럼
직접 단다.

**제목은 나중에 PR 제목이 된다.** 이 레포는 PR 제목을 이슈 제목 그대로 쓴다(최근 5건
전부 일치). 그래서 제목을 여기서 제대로 짓는 것이 뒤에서 한 번 더 안 고민하는 길이다.

생성된 번호로 폴더를 만들고 spec을 옮긴다.

```bash
mkdir -p docs/issues/<번호>-<slug>
```

`<slug>`는 영문 소문자와 하이픈이다. 브랜치 이름의 뒷부분과 같은 것을 쓴다
(`feat/<번호>-<slug>`).

## 안 하는 것

**여기서 브랜치를 만들지 않는다.** 이슈를 만든 것과 그 일을 지금 시작하는 것은 다른
결정이다. 이슈만 쌓아두고 나중에 고르는 것이 정상이다.

**한 번에 이슈 여러 개를 만들지 않는다.** 대화 하나가 이슈 하나다. 회의록에서 항목
다섯 개가 나왔으면 다섯 번 돈다. 한꺼번에 만들면 `배경`이 전부 같은 문장이 되고,
그건 아무도 안 읽는 이슈가 다섯 개 생겼다는 뜻이다.

## 나가는 것

- GitHub issue 번호와 URL
- `docs/issues/<번호>-<slug>/spec.md`
- `gates-ledger.tsv`의 `spec` 행 하나
