인증된 요청마다 DB를 네 번 다녀온다
— 권한 조회 캐시를 왜, 어떻게 도입했나

JWT 필터는 토큰을 검증한 뒤 같은 사용자의 자격증명·계정·개인 권한·부서 권한을 요청마다 DB에서 다시 조립한다. 이 보고서는 그 비용을 운영과 같은 사양의 GCP 복제 환경에서 재고(2부), 캐시를 고른 이유와 가장 큰 위험인 오래된 권한을 어떻게 막았는지(1부), 도입 뒤 무엇이 달라졌는지(3부)를 적는다.

1부 · 왜 도입했나

문제 — 인증 한 번에 나가는 쿼리

토큰 안에 사용자 id가 들어 있지만, 그 사용자가 누구고 무슨 권한을 가졌는지는 매번 다시 읽는다. 화면 하나가 API를 대여섯 개 부르면 인증만으로 스무 번 안팎의 왕복이 붙는다.

  1. user_credentials ⋈ users — 사용자 id로 LOCAL 자격증명 조회
    조인은 WHERE에만 쓰이고 User는 LAZY 프록시로 남는다
  2. users — 같은 사용자 행을 다시 읽음
    credential.getUser().isDeleted()를 읽는 순간 프록시 초기화
  3. user_permissions — 개인 권한
    @OneToMany LAZY 컬렉션
  4. department_permissions — 부서 × 직책 권한
    부서 소속 봉사자·매니저만. 관리자·게스트는 건너뜀
sequenceDiagram
    autonumber

    F->>DB: (컨트롤러) 본문 트랜잭션 — 커넥션을 한 번 더 빌린다

왜 이 비용이 문제인가

  • 모든 인증 요청에 붙는 고정 비용이다. 엔드포인트가 아무리 가벼워도 먼저 네 번 다녀온다. 2부 측정에서 같은 엔드포인트에 토큰만 실어도 요청당 SQL이 1 → 5회, 트랜잭션이 1 → 2개가 됐다.
  • 앱 CPU와 커넥션을 먹는다. 동시 10명에서 처리량이 857 → 484 req/s (−44%), 동시 30명에서는 커넥션 풀(10개)에 평균 19개가 줄을 섰다. 쿼리 하나하나는 0.02~0.06 ms로 싸다 — 비용은 쿼리의 무게가 아니라 횟수 · 엔티티 조립 · 커넥션 점유에서 나온다.
  • 이 데이터는 읽기가 압도적으로 많고 쓰기가 드물다. 역할과 권한은 관리자가 손대야 바뀌는데 조회는 요청마다 일어난다. 결과가 사용자 단위로 나뉘어 캐시 키를 잡기도 쉽다.

가장 큰 위험 — 오래된 권한

캐시에서 제일 위험한 것은 성능이 아니라 권한을 뺏었는데 캐시에 남아 있는 것이다. 그 시간만큼 접근이 열려 있다. 그래서 TTL(5분)만 믿지 않고 바뀌는 순간 지운다. 효과는 테스트로 먼저 확인했다 — 캐시만 붙이고 무효화를 빼면 넷 다 뚫린다.

같은 토큰으로 다시 요청캐시만 (무효화 없음)캐시 + 무효화
개인 권한 user:read:* 회수 뒤200 — 뚫림403
ADMIN → VOLUNTEER 강등 뒤200 — 뚫림403
부서 권한 프리셋 회수 뒤200 — 뚫림403

E2E UserDetailsCacheTest. 무효화를 넣기 전 실행에서 넷 다 실패하는 것을 본 뒤 무효화를 넣었다.

무효화 설계 — 열두 곳 대신 한 곳

역할 · 개인 권한 · 부서 · 삭제 · 자격증명을 바꾸는 코드는 서비스 열두 곳에 흩어져 있다. 거기마다 @CacheEvict를 달면 열셋째 자리에서 빠진다. 대신 그 길들이 모두 지나는 JPA 엔티티 콜백 한 곳에서 지운다.

@PostPersist · @PostUpdate · @PostRemove"}}
    DP --> L
    L -->|"커밋 뒤 (afterCompletion)"| X["userDetails.evict(userId)"]
    L -->|"부서 권한이면"| Y["userDetails.clear()"]
  • 커밋 뒤에 지운다. flush 때 바로 지우면, 커밋 전에 들어온 다른 요청이 아직 커밋 안 된 옛 값을 다시 캐시에 넣는다.
  • 부서 권한이 바뀌면 전체를 비운다. 그 부서 소속만 고르려면 사용자 도메인에 조회가 하나 더 필요하다. 프리셋 변경은 드물고, 비우면 다음 요청에서 한 번씩 다시 채울 뿐이다.
  • 엔티티를 캐시하지 않는다. 값은 id · 이메일 · 권한 문자열만 담은 CustomUserDetails라 지연 로딩 · 분리 엔티티 문제가 없다.

알려진 한계

  • 벌크 JPQL · 네이티브 UPDATE/DELETE는 엔티티 콜백을 우회한다. 네 테이블을 그렇게 고치는 코드를 더하면 그 자리에서 직접 지워야 한다. 지금은 그런 코드가 없다.
  • 커밋 직전에 옛 값을 읽은 요청이 무효화 뒤에 캐시에 쓰면 옛 권한이 최대 TTL 5분 남는다. 창이 수 ms라 막지 않았다.
  • 인스턴스마다 따로 가지는 캐시다. 앱을 여러 대로 늘리면 Redis나 이벤트 기반 무효화로 옮긴다.

안 한 것

  • 부서 권한 전용 캐시 — 사용자 캐시가 hit이면 부서 권한 조회 자체가 안 일어난다. 얻는 것보다 API 변경이 크다.
  • Cloud Monitoring 수집 — 적중률은 /actuator/prometheus의 cache_gets_total로 본다. GCP로 보내는 허용 목록에는 아직 없다.

2부 · 병목 측정

환경 — dev 서버를 그대로 복제

실데이터가 있는 dev 서버에는 부하를 걸지 않았다. 같은 존에 같은 머신 타입으로 VM을 새로 만들고, DB 설정은 dev의 pg_settings에서 기본값과 다른 것을, 데이터는 dev의 테이블별 행 수만 가져와 합성했다.

방법 — 같은 엔드포인트, 토큰만 바꿔서

결과 — 도입 전

해석

흔들리지 않은 것 — 세 번 다 같았다

  • 요청당 SQL: 익명 1회 → 토큰을 실으면 5회 (인증 4회). 내 정보는 9회 — 본문이 인증에서 이미 읽은 users · user_permissions · department_permissions를 다시 읽는다. 필터와 컨트롤러가 트랜잭션을 따로 열어 1차 캐시를 나눠 쓰지 못하기 때문이다.
  • 요청당 트랜잭션: 1 → 2. 인증 요청은 커넥션을 두 번 빌린다 (필터 한 번, 본문 한 번).
  • 커넥션 풀이 줄이 된다: 동시 30에서 풀 10개가 꽉 차고, 인증 시나리오는 평균 19개 · 최대 21개가 커넥션을 기다린다. 동시 10까지는 대기가 0이다.

병목은 DB CPU가 아니라 앱 CPU와 커넥션 풀

  • 2차 측정 동시 10에서 익명 857 → 인증 484 req/s (−44%). 두 경우 모두 앱 CPU가 91%로 꽉 찼고 DB CPU는 18% · 30%였다. 같은 CPU로 처리하는 요청 수가 절반 가까이 줄었다 — 인증 4쿼리의 엔티티 조립 · JDBC · 트랜잭션 비용이 앱 쪽에서 든다.
  • 인증 쿼리 넷은 모두 PK · 인덱스를 타는 단건 조회라 DB에서는 싸다 (평균 0.02~0.06 ms). 비용은 쿼리의 무게가 아니라 횟수와 왕복, 커넥션 점유에서 나온다.

흔들린 것 — 공유 코어 CPU 크레딧

  • 같은 조건(익명 · 동시 10)이 1차 1,095 · 2차 857 · 대조 322 req/s로 흔들렸다. e2-small · e2-micro는 쉬는 동안 쌓인 크레딧으로 순간 성능을 내고, 다 쓰면 vCPU 일부만 받는다.
  • 그래서 DB만 표준 코어로 바꾼 대조 실험은 결론을 못 낸다 — 앞선 측정으로 앱 VM 크레딧이 바닥난 채 돌았다 (앱 CPU 94%인데 처리량 1/3).
  • 도입 후 측정의 설계를 바꾼다: 같은 VM에서 도입 전 · 후 jar를 번갈아(ABAB) 두 번씩 돌리고, 닫힌 모델의 최대 처리량 대신 고정 도착률(실사용보다 높은 50 · 150 req/s)에서 지연 · 쿼리 수 · CPU를 비교한다. 크레딧 상태가 양쪽에 똑같이 걸리게 하기 위해서다.

3부 · 도입 효과

도입 전 jar와 도입 후 jar를 같은 VM에서 번갈아 두 번씩(전 → 후 → 전 → 후) 돌렸다. 공유 코어의 CPU 크레딧 상태가 양쪽에 똑같이 걸리게 하기 위해서다. 최대 처리량이 아니라 고정 도착률(초당 50 · 150건)로 보내, 같은 부하에서 지연 · 쿼리 수 · CPU를 비교한다.

측정의 한계

  • e2-micro · e2-small은 공유 코어라 CPU 크레딧이 남아 있으면 순간적으로 더 빠르다. 구간 사이 20초 쉼으로는 크레딧이 회복되지 않았고, steal에도 잘 드러나지 않는다. 위 「흔들린 것」 참고.
  • 앞단 Caddy(TLS)를 뺐다. 모든 시나리오에 같은 비용이 더해지므로 차이 비교에는 영향이 없다.
  • 합성 데이터는 인증 경로의 행 수만 맞췄다. 다른 테이블의 크기는 이 측정과 상관이 없다.
