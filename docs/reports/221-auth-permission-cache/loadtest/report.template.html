금정야학 플랫폼 API · 이슈 #221 · 성능 측정 리포트

인증된 요청마다 DB를 네 번 다녀온다
— 권한 조회 캐시 도입 전후 부하 측정

JWT 필터는 토큰을 검증한 뒤 같은 사용자의 자격증명·계정·개인 권한·부서 권한을 요청마다 DB에서 다시 조립한다. 운영과 같은 사양으로 GCP에 임시 복제 환경을 만들고, 같은 엔드포인트를 토큰 유무만 바꿔 쳐서 이 고정 비용을 떼어 쟀다.

문제 — 인증 한 번에 나가는 쿼리

토큰 안에 사용자 id가 들어 있지만, 그 사용자가 누구고 무슨 권한을 가졌는지는 매번 다시 읽는다. 화면 하나가 API를 대여섯 개 부르면 인증만으로 스무 번 안팎의 왕복이 붙는다.

  1. user_credentials ⋈ users — 사용자 id로 LOCAL 자격증명 조회
    조인은 WHERE에만 쓰이고 User는 LAZY 프록시로 남는다
  2. users — 같은 사용자 행을 다시 읽음
    credential.getUser().isDeleted()를 읽는 순간 프록시 초기화
  3. user_permissions — 개인 권한
    @OneToMany LAZY 컬렉션
  4. department_permissions — 부서 × 직책 권한
    부서 소속 봉사자·매니저만. 관리자·게스트는 건너뜀

환경 — dev 서버를 그대로 복제

실데이터가 있는 dev 서버에는 부하를 걸지 않았다. 같은 존에 같은 머신 타입으로 VM을 새로 만들고, DB 설정은 dev의 pg_settings에서 기본값과 다른 것을, 데이터는 dev의 테이블별 행 수만 가져와 합성했다.

방법 — 같은 엔드포인트, 토큰만 바꿔서

GET /api/v1/departments는 로그인 없이 열린 엔드포인트지만, 토큰을 실어 보내면 필터가 인증 조회를 그대로 수행한다. 그래서 두 시나리오의 차이가 곧 인증 비용이다. 실사용 경로로 GET /api/v1/users/me를 함께 쟀다.

시나리오요청무엇을 재나
부서 목록 · 익명GET /api/v1/departments본문 비용만

내 정보GET /api/v1/users/me실사용 경로
  • 동시 사용자 1 · 10 · 30, 각 60초. 사이에 20초 쉼. 대기 시간 없이 연달아 보낸다 (닫힌 모델).
  • 측정 전 시나리오마다 30초 워밍업 (JIT · 커넥션 풀 · DB 버퍼).
  • 토큰 58개를 VU마다 나눠 준다. 로그인은 측정 구간 밖에서 미리 한다.
  • 측정마다 pg_stat_statements를 비우고 끝나면 덤프 → 요청당 쿼리 수. 앱·DB VM의 vmstat 1초 표본 → CPU.

결과

해석

흔들리지 않은 것 — 세 번 다 같았다

  • 요청당 SQL: 익명 1회 → 토큰을 실으면 5회 (인증 4회). 내 정보는 9회 — 본문이 인증에서 이미 읽은 users · user_permissions · department_permissions를 다시 읽는다. 필터와 컨트롤러가 트랜잭션을 따로 열어 1차 캐시를 나눠 쓰지 못하기 때문이다.
  • 요청당 트랜잭션: 1 → 2. 인증 요청은 커넥션을 두 번 빌린다 (필터 한 번, 본문 한 번).
  • 커넥션 풀이 줄이 된다: 동시 30에서 풀 10개가 꽉 차고, 인증 시나리오는 평균 19개 · 최대 21개가 커넥션을 기다린다. 동시 10까지는 대기가 0이다.

병목은 DB CPU가 아니라 앱 CPU와 커넥션 풀

  • 2차 측정 동시 10에서 익명 857 → 인증 484 req/s (−44%). 두 경우 모두 앱 CPU가 91%로 꽉 찼고 DB CPU는 18% · 30%였다. 같은 CPU로 처리하는 요청 수가 절반 가까이 줄었다 — 인증 4쿼리의 엔티티 조립 · JDBC · 트랜잭션 비용이 앱 쪽에서 든다.
  • 인증 쿼리 넷은 모두 PK · 인덱스를 타는 단건 조회라 DB에서는 싸다 (평균 0.02~0.06 ms). 비용은 쿼리의 무게가 아니라 횟수와 왕복, 커넥션 점유에서 나온다.

흔들린 것 — 공유 코어 CPU 크레딧

  • 같은 조건(익명 · 동시 10)이 1차 1,095 · 2차 857 · 대조 322 req/s로 흔들렸다. e2-small · e2-micro는 쉬는 동안 쌓인 크레딧으로 순간 성능을 내고, 다 쓰면 vCPU 일부만 받는다.
  • 그래서 DB만 표준 코어로 바꾼 대조 실험은 결론을 못 낸다 — 앞선 측정으로 앱 VM 크레딧이 바닥난 채 돌았다 (앱 CPU 94%인데 처리량 1/3).
  • 도입 후 측정의 설계를 바꾼다: 같은 VM에서 도입 전 · 후 jar를 번갈아(ABAB) 두 번씩 돌리고, 닫힌 모델의 최대 처리량 대신 고정 도착률(실사용보다 높은 50 · 150 req/s)에서 지연 · 쿼리 수 · CPU를 비교한다. 크레딧 상태가 양쪽에 똑같이 걸리게 하기 위해서다.

한계

  • e2-micro · e2-small은 공유 코어라 CPU 크레딧이 남아 있으면 순간적으로 더 빠르다. 구간 사이 20초 쉼으로는 크레딧이 회복되지 않았고, steal에도 잘 드러나지 않는다. 위 「흔들린 것」 참고.
  • 앞단 Caddy(TLS)를 뺐다. 모든 시나리오에 같은 비용이 더해지므로 차이 비교에는 영향이 없다.
  • 합성 데이터는 인증 경로의 행 수만 맞췄다. 다른 테이블의 크기는 이 측정과 상관이 없다.
